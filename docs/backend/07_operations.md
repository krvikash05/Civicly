# Inspection, approvals, municipal actions, monitoring and durable events

## Operational workflow
Complaint -> incident -> investigation -> inspection (when needed) -> hypothesis reassessment -> draft ResolutionPlan vN -> plan `PENDING_APPROVAL` -> human approve/reject exact immutable hash -> validated `ActionTask` READY transitions -> create authorized `WorkOrder` (SIMULATED unless real integration) -> municipal simulated operator starts/updates task and supplies evidence -> verify immediate mitigation/root-cause repair -> monitoring -> verified resolution or re-open.

### WorkOrder vs plan consistency
**Adopt one rule:** `ResolutionPlan`/`ActionTask` are reviewed and approved **before the first WorkOrder is persisted**. New WorkOrder starts at `AUTHORIZED` using a dedicated service operation that atomically ensures referenced approved plan/task, approval hash, department assignment and idempotency. If legacy `WorkOrder` state machine starts at `DRAFT`, update the machine/validator and its tests in B09, do not silently create a different flow. No free-floating work orders created directly from unapproved LLM proposals.

## Inspection lifecycle
Proposal `PROPOSED` (agent analytical write) -> `REQUESTED` by operator or policy -> `SCHEDULED` (authorized inspector/time) -> `IN_PROGRESS` -> `COMPLETED` with attributable observations or `FAILED`. Each report: inspector ID, asset IDs, observed time, measured fields with units, source_kind `SYNTHETIC` in demo, content hash and evidence IDs. Unknown/negative evidence can contradict hypotheses.

Seed `analyst.demo`, `drain.lead.demo`, `sanitation.lead.demo`/`road.lead.demo`, `approver.demo` or equivalent four+ synthetic users. Password/key material outside FalkorDB graph; demo authentication only. Approval never generated by agent acting as a human.

## Plan structure
Plan contains evidence/hypothesis basis; action task IDs, target assets, expected outcome, responsible department, dependency IDs, draft due windows (if sourced), procedure refs, risk/priority, `SIMULATED` mode and monitoring criteria. Validate no DAG cycles, no inactive department, referenced assets/approved version fixed by SHA256. User rejection => agent receives reason and must draft new version; prior approval cannot be reused.

## Monitoring rules (independent from work completion)
- Waterlogging: measure absence or reduction of recurrence in comparable follow-up rain events; if no suitable rain yet status `MONITORING`, not resolved.
- Road: follow-up pavement inspection after simulated wear/test observation; patching alone is `ACTION_COMPLETED`.
- Waste: at least an operational follow-up window of scheduled/actual pickups and no reaccumulation, documented evidence.
- Cases can be `RESOLUTION_VERIFIED` only after the relevant condition policy passes. A new related incident when previously controlled creates `RECURRENCE_DETECTED`, links old repair and reopens, not hides the failure.

## Durable events/outbox
Event types in `contracts/event_types.json`. All events require id, idempotency_key, aggregate/entity ID, graph_revision, occurred_at, source_kind, payload_schema_version. At least: `COMPLAINT_ACCEPTED`, `INCIDENT_LINKED`, `CASE_OPENED`, `GRAPH_EVIDENCE_CHANGED`, `INSPECTION_RESULT_RECORDED`, `PLAN_SUBMITTED`, `PLAN_APPROVED`, `PLAN_REJECTED`, `WORK_ORDER_CREATED`, `WORK_ORDER_STATUS_CHANGED`, `INTERVENTION_OUTCOME_RECORDED`, `MONITORING_DUE`, `RECURRENCE_DETECTED`, `AGENT_RESUME_REQUESTED`.

Single worker processes persisted outbox with claim/lease, retry budget, backoff, DLQ or inspectable `FAILED` terminal; bounded delivery and case-level serialization. **FalkorDB transactional assumptions must be proven**. Fault injection between domain write and event publish must be repaired by reconciliation; cannot claim exactly-once merely through retries. All consumers idempotent. No timer-dependent real-world weather notifications needed: simulation clock/events are explicit and reproducible.

## Simulator safety
Only the simulator test controller may access scenario-specific hidden causes. Its event injection APIs accept selected scenario ID and stage, materialize pre-authored inspection/pickup/rainfall evidence into canonical graph, with `source_kind=SYNTHETIC`, and emit wakeup. It does not write agent hypotheses, plans or expected answers. All simulated physical completion occurs via department actor/work-order route, never an AI declaration.
