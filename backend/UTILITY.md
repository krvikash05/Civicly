# B20-R-UTILITY — synthetic utility intervention

This extends existing B12–B14 planning/operations, B11 document ingestion, B20 responsibility and B16/B18 operator adapters. It is a synthetic demo, not a field operating standard. No new endpoint, role, CLI command, migration, worker or agent is introduced.

`UTILITY_ISOLATION` and `UTILITY_LEAK_REPAIR` apply only to `ROAD_DAMAGE` / `UTILITY_LEAK`, concerned `WaterPipe` targets and `DEPT-WATER`. Both need current reviewed pipe-specific `LEAK_DETECTED` + `INFILTRATION_AT_DAMAGE`, `UTILITY_SAFETY_REVIEWED`, current verified responsibility, a matching retrieved D022 citation and exact human approval/assigned operator. Contradiction, normal pressure, proximity or `UNDERLIES` alone cannot qualify the actions. Source/ownership/assessment/procedure bindings are rechecked before new authority.

A repair task has immutable `CONDITIONAL` remediation with the two current MET causal/safety guards plus `ISOLATION_PROOF` UNMET, `depends_on_task_id` set to the isolation task, and the matching DAG dependency. A draft cannot assert that a future operation already happened. When an approved plan also includes a separately justified `SUBGRADE_REPAIR` on the verified `UNDERLIES` road, that task additionally has `UTILITY_VERIFICATION` UNMET bound to the repair task. Road work still needs its own reviewed subgrade/safety evidence, current road owner, D020 citation and exact approval. An unrelated or unjustified road task is not invented. B05 bounded verified-only traversal establishes dependency scope; truncated topology blocks authority.

Existing order/assignment/START check persisted predecessor completion and reviewed attributable inspection evidence, not just task status. Isolation COMPLETE additionally requires target-bound `UTILITY_ISOLATION_CONFIRMED` and `ACTION_COMPLETED`, independently reviewed and dated after work starts. Its completed inspection must belong to the exact predecessor order, operator and source procedure. Completing isolation alone cannot close a case.

Repair COMPLETE is only `ACTION_COMPLETED` / MONITORING. Through existing work inspection and outcome commands, a distinct authenticated analyst reviews a separate synthetic FOLLOWUP source. A window strictly after completion must contain target-specific `POST_REPAIR_PRESSURE_NORMAL` and `POST_REPAIR_LEAK_ABSENT`. These are qualitative synthetic assertions with no invented numeric units or thresholds. Missing/unknown checks → MONITORING; adverse pressure/leak → PROBLEM_PERSISTS; conflicting checks → INCONCLUSIVE; both positive → UTILITY_VERIFIED under `B20R-UTILITY-1`, `case_closed:false`. Component evaluation is allowed during IN_EXECUTION while road waits. Dependent road authority revalidates stored source/finding hashes, report bindings, completion and verification window. Legacy `B14-2` criteria remain unchanged.

Road completion remains distinct from pavement verification and case closure. Existing independent wear/pavement follow-up is still required; utility verification alone never closes a road incident. Isolation components can count toward final closure only when their corresponding repair has independent utility verification. No B19 scenario, source claim or candidate record was promoted by this change. The primary test adds an explicitly authorized synthetic causal/safety survey to justify road work; this is not additional evidence hidden in the original S04 reveal.

Use existing `plan draft/submit`, `approval decide`, `work create/status/progress/inspect/evaluate/get` and `responsibility submit/review/get` commands with private payload/session files. API bodies use the existing typed routes. D022 is ingested via the existing authorized B11 Memory.ingest mechanism, its manifest checksum is checked, and canonical KnowledgeProcedure remains PROPOSED. Automated author self-review of invented guidance is disclosed; the citation supplies no execution authority.

Source-bound idempotency, exact hashes, fences, durable events, journal and companion integrity, and sanitized UNKNOWN recovery are unchanged. Never redispatch an uncertain key, substitute a new request, delete a record or clear quarantine to finish the workflow. Read the original transport intent/domain operation/journal and retained evidence; obtain supported human reconciliation before any retry. A safe status read does not clear that intent. See `docs/evidence/B20R-UTILITY-WALKTHROUGH.md` for focused reproduction and actual IDs.


## B20-R-UTILITY-R single-predecessor limit
A road task supports at most one relevant utility-repair task across all its targets. The existing bounded verified-only topology traversal discovers all such tasks; more than one fails closed with `UTILITY_MULTIPLE_REPAIR_PREDECESSORS`. A sole linked repair must be the exact UTILITY_VERIFICATION condition predecessor and depends_on binding, with topology covering every target. No linked repair retains ordinary independently qualified road behavior. Multiple linked repairs are an unsupported scope under the current one-predecessor contract: do not select one, omit a relevant repair or treat approvals as a workaround. A separately reviewed design/scope is required; no general multi-predecessor schema is introduced. Planning and existing Operations.validate recheck this policy using current topology before new authority. Historical drafts, approvals, hashes and receipts are never rewritten.
